# HyperDB portability audit

Status: Stage 1 audit with implementation follow-up, updated 2026-11-01. Baseline audit: local `main` at `78177b2` (which includes `fc70211` and `08e16a9`). The initial baseline Linux Debug build passed 15/15 tests. Since the baseline, commits `39f2eb9`, `38c9d68`, `db34bff`, `a79b611`, and `30060ca` recorded the audit, target architecture, adapter splits, and initial C API. Current Linux Debug and Release each pass 17/17 tests. This document describes observed code and tests, not target-platform support.

## 1. Current architecture and functionality

HyperDB currently has one C++20 in-memory SQL engine. [`Database`](../../src/database/database.h#L13) owns maps of tables, in-memory B-trees, and exact vector indexes. [`Value`](../../src/database/TableData/value.h#L9) holds NULL, signed 64-bit integer, double, string, or byte vector. `Schema` stores columns and case-folded lookup names. The CLI and Python bridge use the same SQL implementation. An initial opaque C API now wraps in-memory execution; it has no prepared-statement or storage injection interface. The experimental page modules are not used by SQL or snapshot persistence.

Repository scope inspected: all files under `src/` and `include/`, CMake and presets, `.github/workflows/ci.yml`, C++ and Python test targets, fuzz target and seeds, examples, benchmark sources, existing architecture/status/limitation documents, and Python UI/bridge/training scripts. The Python local UI runs the CLI through `subprocess` and a local `ThreadingHTTPServer`; the Streamlit demo uses optional model packages and the bridge. Neither is part of the embedded engine core.

Observed SQL support: one-statement `SELECT`, `CREATE TABLE`, one-row `INSERT`, `UPDATE`, and `DELETE`; one optional two-table inner join; comparison and three-valued boolean predicates; `IS NULL`; projection; one-column `ORDER BY` and `GROUP BY`; `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, aggregate `HAVING`, and `LIMIT`. Simple equality predicates can use an in-memory B-tree. Vector search is exact cosine similarity over caller-supplied embeddings. The tests cover representative behavior, not full SQLite semantics. SQL index DDL, aliases, outer joins, range index scans, general expressions, multi-statement transactions, and SQL primary-key uniqueness are absent. Column type names are metadata; coercion is not enforced. Sources: [parser AST](../../src/parser/ast.h#L14), [query executor](../../src/QueryExecutor/query_executor.cpp#L181), [statement executor](../../src/QueryExecutor/statement_executor.cpp#L10), [database](../../src/database/database.cpp#L33), and [README](../../README.md).

Execution pipeline: SQL string → [`tokenize`](../../src/parser/lexer.cpp#L226) → [`parse_statement`](../../src/parser/parser.cpp#L323) → name and predicate validation → optional nested-loop join → scan or equality-index candidates → filter → projection or grouping/aggregation → optional sort → limit → fully materialized `QueryResult`. The parser has no OS calls. The executor reads in-memory `Table.rows`; it does not use a pager. [`QueryResult`](../../src/QueryExecutor/query_executor.h#L10) returns all result rows in a vector.

## 3. Storage, persistence, and device assumptions

The active compatibility persistence path is [`Database::save/load`](../../src/database/persistence.cpp#L145), built as `hyperdb_snapshot_compat` rather than in `hyperdb_core`. It serializes a versioned `HDBSNAP1` stream in little-endian integer order, writes a temporary sibling, flushes and closes it, calls POSIX `fsync` on Unix, renames it over the destination, and syncs the directory on Unix. Loading checks a 1 GiB file cap, table/row/column and field caps, and rejects malformed values and trailing bytes. It rebuilds B-trees in memory. The CLI uses a POSIX advisory `.lock` file across load/execute/save ([main.cpp](../../src/main.cpp#L23)). There is no transaction log, torn-write oracle, power-loss test, or library-level lock. The non-Unix `sync_path` branch performs no sync; rename-replacement behavior is not established on Windows. Each successful CLI write rewrites the whole snapshot.

The separate page path uses fixed [8192-byte pages](../../src/storage/page_format.h#L12), explicit little-endian fields, CRC32C trailers, a versioned page-zero header, and append-only slotted records. [`DiskManager`](../../src/storage/disk_manager.cpp#L17) maps page IDs to byte offsets, syncs an initialized page before publishing the header count, and tolerates orphan tail bytes on reopen. [`BufferPool`](../../src/storage/buffer_pool.cpp#L25) caches copies of pages and calls an abstract WAL durability hook before a dirty write. There is no WAL implementation, page reclamation, overflow record format, database catalog, page-backed B-tree, checkpoint protocol, or crash recovery. The file interface assumes random byte-addressable reads/writes, complete-or-error transfer, a meaningful file size, and `sync` ([file_system.h](../../include/hyperdb/file_system.h#L13)). It exposes no program/erase geometry, alignment, atomic-write unit, capacity, bad-block behavior, or sync guarantee. Therefore it is a filesystem-like interface, not yet a raw-flash contract.

## 4. Memory, allocations, and ownership

The current engine uses system `new` through STL containers. `Database` owns all tables, index nodes, and embeddings; rows own all values; the parser owns its AST via `unique_ptr`; `QueryResult` owns all output rows. No application allocator, fixed pool, arena policy, global budget, per-query budget, or measured peak-memory contract exists. `BufferPool::create` allocates `capacity` frames, each containing an 8192-byte `Page`, but reads and writes copy another page by value. A 32 KiB total-memory claim is therefore unsupported.

These are concrete low-memory correctness risks to test before claiming fixed-memory operation.

## 6. Concurrency and blocking behavior

The `Database` API is not synchronized and has no connection/session abstraction. The CLI serializes cooperating processes with an advisory sidecar `flock`. The file adapter claims thread-safe positioned I/O; the disk manager serializes allocation with `std::mutex`, while the buffer pool serializes cache operations with another `std::mutex`. No lock ordering contract, priority-inversion policy, timeout, cancellation, or reader/writer isolation exists. `fsync`, file I/O, full snapshot load/save, sort, join, and scan can block for unbounded time relative to RTOS deadlines. There are no background worker threads in production code. Tests create threads for allocation checks.

## 8. Missing components and measured performance

An embedded database still needs: resource-configured connection handles, prepared execution, a bounded row iterator, page-backed heap/catalog/indexes, a real pager, transaction/recovery implementation, platform-provided memory/storage/synchronization, stable C ABI, and compatibility migration. RTOS integration additionally needs a no-thread core build, storage geometry/flash contract, caller-controlled blocking and lock policy, tested allocator-failure behavior, and a representative adapter test. None is yet proven on hardware.

The only recorded performance data are narrow local workloads: [BENCHMARKS.md](../BENCHMARKS.md) records 20,000-row in-memory scans, sorts, groups, joins, and 5,100-row snapshot operations on one Linux laptop. [Optimization history](../../optimizatoons.md) notes improvements and measurement gaps. No peak-memory, cache hit-rate, transaction throughput, flash write-amplification, or portable cross-target benchmark is recorded. The storage prototype has no SQL throughput result. Do not infer SQLite parity or embedded performance from the available figures.

## 9. Prioritized dependency plan

1. Establish a shared core/platform build boundary and adapter contract, with a native in-memory fake and no-filesystem compile gate. Preserve the current SQL core and POSIX CLI behavior.
2. Add allocation-free status codes and explicit resource configuration. Use deterministic failure injection before claiming fixed-memory behavior.
3. Add stable C handles and prepared-statement lifecycle around the same core, with C and C++ embedding examples and ABI tests.
4. Define storage capability/geometry and select a recovery protocol for filesystem and flash-backed adapters. Validate power-cut ordering before replacing snapshots.
5. Move tables, catalog, and indexes onto the pager incrementally; keep a tested migration reader for `HDBSNAP1`.
6. Add bounded execution and memory budgets without changing SQL semantics; explicit resource exhaustion is the expected outcome for oversized operations.
7. Validate native Windows, cross-compiled embedded, representative RTOS, and eventually hardware targets separately. Record actual memory peaks and performance before target-support claims.

Stage 1 is an audit and plan. It does not satisfy any target-platform acceptance criterion by itself.
