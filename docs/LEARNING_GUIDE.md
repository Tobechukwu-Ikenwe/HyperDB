# Learning guide

Build first with the commands in `README.md`. After each exercise, run `ctest --test-dir build --output-on-failure`.

1. **Rows, schemas, and ownership.** Read `src/database/TableData/{value,row,column,schema,table}.h`, `src/database/database.{h,cpp}`, and `tests/database_tests.cpp`. Trace `create_table`, `find_table`, and `insert_row`. Exercise: predict which malformed rows are rejected and why callers get a `const Table*`. What does declared affinity do today?
2. **Tokens and syntax.** Read `src/parser/{lexer,parser,ast}.{h,cpp}` and their tests. Draw the AST for `a=1 OR b=2 AND NOT c=3`. Exercise: add a malformed join or aggregate query test and predict its line/column. Which mistakes require a schema to detect? Why does `x = NULL` differ from `x IS NULL`?
3. **Writes and invariants.** Read `src/QueryExecutor/statement_executor.cpp`, `Database::replace_rows`, and `tests/statement_tests.cpp`. Use the README commands to create, insert, update, restart, and query. Why does DELETE remap embeddings? What happens when an UPDATE tries to put NULL in a required column?
4. **Relational execution.** Read `src/QueryExecutor/{query_executor,aggregate}.cpp` and `tests/database_tests.cpp`. Trace a join with a grouped count, including NULL handling. Exercise: explain why `COUNT(*)` differs from `COUNT(amount)` and why `ORDER BY` precedes `LIMIT`. Compare one fixture result with SQLite, then read `tests/sqlite_conformance.py` and explain why its first floating-point display comparison needed normalization.
5. **Indexes and planning.** Read `src/database/Indexes/{btree,btree_node,index_entry}.h`, `btree.cpp`, `tests/index_tests.cpp`, and `benchmarks/benchmark.cpp`. Draw a node split for minimum degree two. Exercise: predict when `index_candidates` returns `nullopt` versus an empty vector. Why does the executor still evaluate the predicate after fetching row IDs?
6. **Snapshots and restart.** Read `src/database/persistence.cpp` and `tests/persistence_tests.cpp`. Save the CLI demo, query it in another process, then truncate a copy and observe load failure. Why are index definitions saved while B-tree nodes are rebuilt? Why does the CLI retain its `.lock` file? Why are both the temporary file and its directory synced? What would a WAL add?
7. **Vector retrieval.** Read `src/database/Indexes/vector_index.{h,cpp}`, `examples/vector_search.cpp`, and `tests/vector_tests.cpp`. Exercise: compute the three cosine scores in the test by hand. What would be required to store real model embeddings durably? When would exact scanning stop being adequate?
8. **Python/model boundary.** Read `python/{model,inference,app,hyperdb_bridge}.py`, `src/bridge/sqlite_bridge.cpp`, and `tests/bridge_tests.py`. Exercise: draw the data transfer from a read-only SQLite file to a C++ result. Try a supported query and an unsupported one. Explain why generated SQL can fail even if the model runs successfully.
9. **Measurement and data provenance.** Run both commands in the README benchmark section and inspect `benchmarks/sqlite_baseline.py`. State exactly what each timing includes. Run `python3 python/inspect_insurance.py`, then read `docs/DATA_PROVENANCE.md` and run the slower `python3 python/verify_insurance.py`. Explain which local integrity claims are proven and which external-origin claims remain unverified.

Interview check: explain the end-to-end query path, AST ownership, table invariants, NULL and aggregate semantics, B-tree split/lookup, vector search complexity, bridge limits, one measured performance result with caveats, and the largest remaining architecture decision.
